The 3am Page Where Nothing Was Broken

The thing that started your outage stopped twenty minutes ago. Something else has been keeping it alive.

Step 1 · Managing Working Memory

Two words your postmortem probably uses interchangeably

You were paged at 3am. By the time you had a laptop open, the database was healthy, the deploy was hours old, the dependency dashboards were green, and the latency graph was still pinned at the top. Everyone on the call asks the same question: so what is broken? Nothing is. That sentence is only confusing if you are holding one idea where there are two.

The trigger

What pushed the system out of its normal state

A 20-second garbage-collection pause. A cache that came back cold. One slow dependency. Triggers are usually small, usually brief, and usually gone before you finish reading the alert. This is the thing everyone hunts for, and it is the thing that stops mattering first.

The sustainer

What keeps the system out, once it is out

A feedback loop that the trigger switched on and that now feeds itself. It needs no ongoing fault, no bad deploy, and no unhealthy host. It will happily run for hours on a perfectly healthy fleet, which is exactly why your dashboards look fine.

Hold only these two. An outage with a live trigger is a fault you can find and fix. An outage whose trigger is gone is a loop you have to break, and the two call for opposite actions. Mixing them up is what turns a 90-second blip into the four-hour incident you are going to write up tomorrow.

Step 2 · Cognitive Offloading

One arrow in, four arrows going round

Do not try to hold this shape in your head at 3am. Look at where the arrows go instead. The trigger has exactly one arrow, pointing in. Everything after it forms a ring, and a ring does not need its entrance to keep turning.

Follow the ring once, slowly. Latency rises, so requests cross the client deadline. A client that has timed out cannot tell a slow success from a real failure, so it does the only safe thing available to it and asks again. That retry is a brand new request, and the original one is very often still sitting on a server thread. One user action is now costing you two or three units of work.

So the queue grows. And every request waiting behind that queue is slower than it was, which is the arrow from Queue depth back to Latency rises. That single arrow is the whole page. It is what makes this a ring instead of a line, and it is what lets the outage outlive the twenty seconds that started it. The industry name for a system stuck in this state is a metastable failure: stable, self-sustaining, and built entirely out of healthy components.

Step 3 · Conflict Resolution

The Reliability Trap

Here is where the naive model gets people, and it gets good engineers most of all, because the move it suggests is the move that reliability training rewards.

03:14 · the change that lengthened the outage

Requests are timing out, so you make the client more patient and more persistent. You raise the timeout from 1s to 5s so calls stop being cut off early, and you bump retries from two attempts to three so a request has a better chance of getting through.

Both changes are defensible in isolation. Together they are the two gain knobs on the loop, and you just turned them up. The longer timeout means each doomed request occupies a server thread five times as long before anyone gives up on it. The extra attempt raises the work multiplier from 3x to 4x. Queue depth climbs faster than before.

At 03:22 someone restarts the service. Latency drops beautifully for about thirty seconds. Then it collapses again, because the retry backlog is still out there and it refills the empty queue immediately. The restart cured nothing; it just gave the loop a clean queue to fill.

You have spent eight minutes making the outage worse, using two changes that both read as "improve reliability" in the commit message.

Resolve it by asking what the action does to the ring, not to the request in front of you. A loop sustains itself while its gain stays above one: while each pass produces more work than the last. Every effective mitigation attacks that number, and every one of them feels wrong at 3am because each involves serving less traffic on purpose.

Shed load, so the queue drains below the depth that sustains the ring. Open a circuit breaker, so clients stop generating retries at all. Cap retries with a real retry budget, which permits retries only up to a small fraction of live traffic and refuses the rest. Add jitter, so the retries you do allow stop arriving in synchronised waves. Note that a retry budget is a ceiling on the loop, not a permission to retry more; it is the fix, and it is easy to hear the name and reach for the opposite.

And the useful thing about all of this: it tells you the trigger is often not worth chasing during the incident. Find it tomorrow. Tonight, break the ring.

Step 5 · Active Re-encoding

Build the ring yourself, and say why each arrow exists

In a week you will be standing in a postmortem review defending a claim: that the outage lasted three hours because of a loop, not because of the twenty-second pause that everyone in the room wants to talk about. Nobody will accept the diagram. They will accept the because on each arrow, and only if you can produce it without notes.

So the boxes below are given to you and every arrow is missing. Tap one box, then another, to draw an arrow between them, and type the reason it exists. An arrow with no reason stays dashed and does not count.

0 of 5 edges explained

    Draw all five arrows and write a because on each one before you open the reveal. Four of them are easy. The fifth is the one that closes the ring, and if you cannot find which arrow that is, you cannot yet make the argument this page exists to teach.
    I have drawn all five. Show me the reference.

    Latency rises → Clients hit their deadline. Because the client deadline is a fixed number chosen when things were fast. Nobody moved it; the latency moved underneath it.

    Clients hit their deadline → Every client retries. Because a timed-out client cannot distinguish a slow success from a lost request, so retrying is its only safe move. This arrow is correct behaviour, not a bug.

    Every client retries → Queue depth grows. Because a retry is a new request while the original is usually still occupying a server thread. One user action becomes three units of work.

    Queue depth grows → Latency rises. Because queueing delay is added to every request waiting behind it. This is the arrow that closes the ring, and it is the reason the outage survives the death of its own trigger. If you produce only one arrow in that postmortem, produce this one.

    Latency rises → The page fires. Because your alert watches the symptom, not the cause. It is reading the loop's output, which is why it tells you something is wrong and never which arrow to cut.

    Notice what has no arrow into it at all: the trigger. It is not on this diagram, and that is the point.
