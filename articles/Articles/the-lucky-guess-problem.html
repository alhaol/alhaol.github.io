The Lucky Guess Problem

Assessment works only when right answers are rarely lucky. AI makes them lucky on demand, so shipped code no longer shows what a team knows.

Ibrahim AbuAlhaol

November 9, 2026 · 5 min read

Key takeaways

  1. Knowledge Space Theory's assessment models give every item a lucky-guess rate, and reading a state from answers works only while that rate stays low.
  2. Engineers who learned a new async Python library with AI help averaged 50% on a follow-up quiz, against 67% for those who coded by hand.
  3. Across nine experiments, searching the internet led people to mistake access to information for their own understanding, and an assistant is that access, always on.

A platform team moves a service to async Python with heavy help from a coding assistant. The pull requests are clean and the migration ships a sprint early. Three months later a request hangs in production, and nobody on the team can explain how cancellation travels through the task tree. Every review, skill matrix and promotion packet had treated the merged code as evidence that the team understood it. It was evidence that the code worked.

Knowledge Space Theory explains the gap between the two. Its assessments infer what a person knows from their answers, and they can do it with few questions only because a right answer is rarely a lucky guess.1 AI assistance makes lucky guesses cheap and constant. A team's output now says little about its knowledge state, so leaders who need that state have to measure it, and the assistant can do the measuring.

Assessment assumes lucky guesses are rare

In the theory's most studied probabilistic model, every item carries two error rates: the chance that someone who knows it answers wrong anyway, a careless error, and the chance that someone who does not know it answers right, a lucky guess.1 When both are small, each answer is strong evidence, and an adaptive assessment can locate a person quickly. ALEKS, built on the theory, pinned down one student's state among 57,147 candidates with 24 questions.2

Engineering organizations run the same inference informally. A merged pull request, a resolved incident, a design that survived review: each is read as an answer that reveals a knowledge state. Promotion packets are assembled from them and skill matrices updated from them. The inference was always noisy. It held up because writing correct code you did not understand used to be hard.

AI makes every answer a possible guess

A coding assistant raises the lucky-guess rate on every task it can do. Suppose half a team understands cancellation, careless errors run at 10% and lucky guesses at 10%. Then 90% of right answers come from someone who knows the concept. Now let an assistant push the lucky-guess rate to 90%. Right answers nearly double, and only 50% of them come from knowing, no better than picking an engineer at random (Figure 1).

Experiments show the effect on exactly this kind of work. Researchers at Anthropic randomly assigned developers to learn a new asynchronous programming library with or without AI assistance.3 The 52 mostly junior engineers were all unfamiliar with Trio, the library in question.4 The AI group finished about two minutes faster, a difference that was not statistically significant, and then averaged 50% on a quiz about the library, against 67% for those who had coded by hand.4 Same task, a different state at the end.

School mathematics shows the same split. In a trial with nearly 1,000 students, unrestricted GPT-4 raised practice grades by 48%, then left those students 17% behind peers who never had it once access was removed.5 People rarely notice the gap from inside. Across nine experiments, searching the internet for explanations led people to mistake access to information for their own understanding.6 An assistant is that access, always on (Figure 2).

Turn the assistant into the assessor

The tool that masks the state can also measure it. After a change merges, an assistant can read the diff, list the concepts the code depends on, and write three to five short probes on them: predict what this coroutine does when its parent is cancelled, explain why this lock exists, find the bug in a ten-line variant. The engineer answers without help.

The probes adapt as an ALEKS assessment does, and the result is a state with an outer fringe rather than a score: the concepts this engineer is ready to learn next. The Missing Edge describes how a few such questions find the prerequisite a person lacks.

For the async migration, the probes would have asked what happens to a child task when its parent's scope is cancelled, and where a timeout belongs. The engineers who wrote that code would have learned they could not answer while the code was still fresh, months before a hung request taught them in production.

How the assistant is used matters as much as the probes. In the Trio study, the participants who showed stronger mastery used the assistant to build comprehension, asking follow-up questions, requesting explanations or posing conceptual questions while they coded.4 Vendors now ship modes that push in the same direction. Anthropic's learning mode guides a student's reasoning instead of providing answers,7 and OpenAI introduced a study mode for ChatGPT in July 2025.8 The probes are drafts too: a reviewer should drop any that test trivia instead of an edge the code depends on.

Keep the result with the engineer. The point is to show people their own missing edges before an incident does. Ranking them defeats the purpose. A team-level view, aggregated and anonymous, is enough to show leaders where the shared gaps sit, which is the map The Map Nobody Drew asks teams to build.

Some prerequisites deserve to go

The strongest objection is the calculator argument. Few engineers are tested on memory layout or assembly anymore, because abstraction retired those prerequisites, and AI may retire many more. Probing for knowledge the job no longer needs is nostalgia, and probing people at all can feel like surveillance.

Both points are fair, and both sharpen the practice instead of ending it. Some edges can be delegated for good, the way most engineers delegate memory management to a runtime. The ones that cannot are the edges oversight runs on: reading a diff critically, debugging a failure, deciding during an incident. In the Trio study, the largest gap between the two groups was on debugging questions.4

Decide edge by edge which knowledge must stay in people's heads, probe only that set, and let the rest go. Reviewing AI work at a higher level, as Abstraction Is the Review Layer argues, still needs someone who knows what the level hides.

Every review, skill matrix and promotion packet had treated the merged code as evidence that the team understood it. It was evidence that the code worked.

What leaders should do

  1. List the concepts each critical service's on-call rotation depends on, and mark the oversight edges that must stay in engineers' own knowledge states.
  2. Add three to five unaided probes, generated by the assistant from the diff, to merges that touch an oversight edge, with results visible only to the author.
  3. Stop citing merged pull requests alone as evidence of mastery in promotion packets; pair them with a debugging session or design review the candidate leads without assistance.
  4. Track the share of incidents whose responders could explain the failing mechanism without an assistant, and treat a falling share as a training signal.
